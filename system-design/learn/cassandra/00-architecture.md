## Architecture at a glance

Before the data model, see the system an architect would draw. This is a chat app that keeps
every message in Cassandra, with a second region and a separate analytics DC. The message
service writes each message once; Cassandra handles the copies. Play the figure, then switch the
tabs: a New Year's Eve spike, a node going down, and a node being added to the ring.

### How it scales

The cluster grows by adding nodes, never by moving to a bigger box: three nodes, then a larger
rack-aware ring, then a second region, then a separate DC just for analytics.

### Design decisions

| Decision | Options | Choice | Why |
|---|---|---|---|
| Partition key | conversation_id · (conversation_id, time bucket) · user_id | **(conversation_id, bucket)** | One seek for the latest page, and busy group chats can't grow one partition forever |
| Message id | server counter · client-generated time UUID | **Time UUID** generated by the service | Sorts by time, needs no coordination, and makes retries idempotent |
| Consistency | ONE · LOCAL_QUORUM · EACH_QUORUM · ALL | **LOCAL_QUORUM** for writes and reads | R + W > RF inside the DC, with no cross-region wait |
| Replication | RF 2 · RF 3 per DC | **RF 3 per serving DC**, RF 1 in analytics | Survives one node down per DC with quorum intact |
| Analytics | scan the serving DCs · separate analytics DC | **Separate DC** | Full scans can't evict caches or saturate disks on serving nodes |
| Fan-out | inside the write request · through a queue | **Queue + push workers** | A big group chat doesn't slow down the sender's write |

### Risks and mitigations

| Risk | Trigger | Impact | Mitigation |
|---|---|---|---|
| Oversized partition | a very busy group chat | Slow reads, heavy compaction, a hot replica set | Time-bucket the partition key; alert on partition size |
| Compaction debt | a write spike | Reads touch many SSTables; p99 climbs | Disk and CPU headroom, a compaction strategy that suits the workload, scale before known peaks |
| Deleted data comes back | a node is down longer than gc_grace and misses deletes | Deleted messages reappear | Run repair on every node within gc_grace; rebuild nodes that were down too long |
| Stale cross-region read | user writes in one DC and reads in another | A sent message seems missing | Home DC per user, or show pending sent messages on the client |
| Tombstone build-up | deleting many rows in a partition | Reads scan thousands of tombstones and time out | Prefer TTLs and time buckets to row-by-row deletes |
| Uneven nodes | a skewed partition key, or nodes of different sizes | One node fills first | Keys with high cardinality, vnodes, the same hardware across a DC |
